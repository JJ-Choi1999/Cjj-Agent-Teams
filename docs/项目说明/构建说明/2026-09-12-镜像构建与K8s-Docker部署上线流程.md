## 一、结论速览（一页版）

AgentTeams 有**两条并列的部署路径**，镜像构建方式完全相同，区别只在"谁来拉起容器"：

| 路径 | 形态 | 入口 | 谁创建 Worker |
|---|---|---|---|
| **Docker（本地 embedded）** | 单容器 all-in-one（Higress+Tuwunel+MinIO+Element Web+Controller）+ 独立 Manager 容器 + 按需 Worker 容器 | `install/agentteams-install.sh`（或 Windows `.ps1`） | Controller 通过挂载的 Docker socket / Docker Proxy |
| **Kubernetes** | 每个组件独立工作负载（Pod/StatefulSet/Deployment），由 Helm 部署 | `helm/agentteams/`（`helm upgrade --install`） | Controller 通过 K8s API 创建 Worker Pod |

核心事实：

1. **没有 docker-compose**。本地部署靠 `install/agentteams-install.sh` 以 `docker run` 拉起 `agentteams-embedded` 单容器（基础设施 + controller），再拉起 Manager 容器，Worker 按需创建。
2. **Manager 与 Worker 在 K8s 中不是静态 Deployment**。Helm 只创建 Controller Deployment 与一个 `Manager` CR；Manager Pod、Worker Pod 由 Controller 依据 CR 动态生成。
3. **镜像构建有依赖顺序**：`agentteams-controller`（提供 `agt` CLI）与 `openclaw-base` 必须先构建，manager/worker 才能构建。
4. **默认仓库**：`higress-registry.cn-hangzhou.cr.aliyuncs.com/agentteams`；默认版本 `VERSION=latest`。
5. **多架构是默认行为**：`make push` 构建并推送 `linux/amd64,linux/arm64` 多架构清单。
6. **CI 触发**：打 `v*.*.*` tag 自动构建推送全部镜像并发布 Release。

## 二、镜像清单与构建依赖图谱

### 2.1 镜像总表

| Makefile 目标 | 镜像名（`$(REGISTRY)/$(REPO)/` 前缀） | Dockerfile | 基础镜像 | 多阶段 |
|---|---|---|---|---|
| `build-openclaw-base` | `openclaw-base` | `openclaw-base/Dockerfile` | `higress/ubuntu:24.04` | 否 |
| `build-agentteams-controller` | `agentteams-controller` | `agentteams-controller/Dockerfile` | `golang:1.25-alpine` → `alpine:3.20` | 是（4 stage） |
| `build-embedded` | `agentteams-embedded` | `agentteams-controller/Dockerfile.embedded` | 依赖 controller 镜像 | 是 |
| `build-manager` | `agentteams-manager` | `manager/Dockerfile` | `openclaw-base` | 是（2 stage） |
| `build-manager-qwenpaw` | `agentteams-manager-qwenpaw` | `manager/Dockerfile.qwenpaw` | `python:3.11-slim` | 否 |
| `build-worker` | `agentteams-worker` | `worker/Dockerfile` | `openclaw-base` | 是（2 stage） |
| `build-copaw-worker` | `agentteams-copaw-worker` | `copaw/Dockerfile` | Python 基底 | 是（双 venv） |
| `build-qwenpaw-worker` | `agentteams-qwenpaw-worker` | `qwenpaw/Dockerfile` | `python:3.11-slim` | 否 |
| `build-hermes-worker` | `agentteams-hermes-worker` | `hermes/Dockerfile` | `python:3.11-slim` | 是 |
| `build-openhuman-worker` | `agentteams-openhuman-worker` | `openhuman/Dockerfile` | `rust:1.93-bookworm` → `debian:bookworm-slim` | 是（4 stage） |
| `build-deepseek-harness-worker` | `agentteams-deepseek-harness-worker` | `deepseek-harness/Dockerfile` | `node:22.22-bookworm-slim` | 是 |

> 本地（未推仓）镜像名不带 registry 前缀，例如 `agentteams/manager:$(VERSION)`、`agentteams/worker-agent:$(VERSION)`、`agentteams/agentteams-controller:$(VERSION)`。

### 2.2 构建依赖图谱

```
openclaw-base ──┬──> manager (OpenClaw 版)      ──┐
                └──> worker (OpenClaw Worker)     │
                                                   │
agentteams-controller ──┬──> (提供 /usr/local/bin/agt) ──> manager / worker / copaw / qwenpaw / hermes / dsh / openhuman
                        └──> agentteams-embedded ──> install/（本地 Docker 部署）

shared/lib/*.sh        ──> 全部运行时镜像（COPY --from=shared 或 COPY shared/lib/）
plugins/teamharness/adapters/qwenpaw        ──构建期打包──> qwenpaw-worker
plugins/teamharness/adapters/deepseek-harness ──构建期 pack──> deepseek-harness-worker
```

**含义**：改 `openclaw-base` 需重建 manager/worker；改 controller 需重建全部含 `agt` 的镜像；改 `shared/lib` 需重建全部运行时镜像。CI 中该依赖关系由 `.github/workflows/build.yml` 的 `dependencies` 字典强制保证。

## 三、Docker 镜像构建（Dockerfile 与 Makefile）

### 3.1 基础镜像选择策略

| 基础镜像 | 用于 | 选择原因 |
|---|---|---|
| `${HIGRESS_REGISTRY}/higress/ubuntu:24.04` | `openclaw-base` | 纯 Ubuntu（约 100MB），避免旧的 all-in-one 基底（含 Higress/Envoy/Pilot，约 1.7GB）拖慢 Manager/Worker |
| `higress/golang:1.25-alpine` | controller 构建阶段 | 与 `go.mod` 的 Go 1.25 对齐 |
| `higress/alpine:3.20` | controller 运行阶段 | 极小运行时，仅装 `bash jq curl unzip kubectl` |
| `python:3.11-slim` | qwenpaw / hermes / manager-qwenpaw | Python Worker 运行时基线 |
| `node:22.22-bookworm-slim` | deepseek-harness | 与 `@deepseek-ai/dsh` 的 Node 版本对齐 |
| `rust:1.93-bookworm` → `debian:bookworm-slim` | openhuman | Rust 编译产物与精简运行时分离 |

`HIGRESS_REGISTRY` 是**构建参数**（默认 `higress-registry.cn-hangzhou.cr.aliyuncs.com`），用于国内拉取加速；北美/东南亚有对应镜像域（见 `Makefile` 顶部注释）。

### 3.2 多阶段构建要点

以 controller 镜像为例（`agentteams-controller/Dockerfile`），四阶段各司其职：

| 阶段 | 作用 | 关键点 |
|---|---|---|
| `builder` | 编译 `agentteams-controller` 与 `agt` | `CGO_ENABLED=1` 生成静态 controller；`CGO_ENABLED=0` 生成可移植 `agt`；`GOPROXY` 可覆盖 |
| `mc` | 提供 MinIO Client 二进制 | 从 `higress/mc:20260216` 拷贝 |
| `kube-bin` | 下载 `kube-apiserver`（embedded 模式自举用） | `FROM --platform=$BUILDPLATFORM` 固定构建平台，避免 QEMU 下 TLS 异常；用 `TARGETARCH` 选架构 |
| `final` | 组装最小运行镜像 | 拷贝四个产物 + CRD 源（`config/crd/`）+ agent 模板（`agent/`）；`ENTRYPOINT ["agentteams-controller"]` |

Worker / Manager 采用"**依赖镜像借用 + 单一运行层**"模式：

```dockerfile
# worker/Dockerfile 节选
FROM ${HIGRESS_REGISTRY}/higress/mc:20260216 AS mc
FROM ${AGENTTEAMS_CONTROLLER_IMAGE} AS agentteams-controller
FROM ${OPENCLAW_BASE_IMAGE}
COPY --from=mc /usr/bin/mc /usr/local/bin/mc.bin
COPY --from=agentteams-controller /usr/local/bin/agt /usr/local/bin/agt
COPY --from=shared . /opt/agentteams/scripts/lib/
```

要点：
- **`OPENCLAW_CMS_PLUGIN_URL` 层被刻意放在 `COPY scripts/lib` 之前**，避免代码改动使这层缓存失效。
- Worker 会把 `lsof` 替换成 stub（`exit 1`），规避 Kind / Docker-in-Docker 下 `lsof` 扫描 `/proc` 卡死。
- Worker 通过符号链接把 `mc` 指向 `mc-wrapper.sh`，实现每次调用前自动刷新 STS 凭据（embedded/K8s 云模式下生效，本地模式为空操作）。

### 3.3 构建参数（build-arg）总表

| 参数 | 默认值 | 作用 |
|---|---|---|
| `HIGRESS_REGISTRY` | `higress-registry.cn-hangzhou.cr.aliyuncs.com` | 基底镜像仓库（区域镜像） |
| `OPENCLAW_BASE_IMAGE` | `$(REGISTRY)/$(REPO)/openclaw-base` | OpenClaw 基底镜像地址 |
| `OPENCLAW_BASE_VERSION` | `20260423-8359cbc`（Makefile 内置） | 基底镜像 tag |
| `AGENTTEAMS_CONTROLLER_IMAGE` | `agentteams/agentteams-controller:latest` | 提供 `agt` 的镜像 |
| `BUILTIN_VERSION` | `$(VERSION)` | 写入 `/opt/agentteams/agent/.builtin-version`，驱动启动期 builtin 升级 |
| `APT_MIRROR` | 空 | 国内 APT 加速（如 `mirrors.aliyun.com`） |
| `NPM_REGISTRY` | `https://registry.npmjs.org/` | 国内 NPM 加速（如 `https://registry.npmmirror.com/`） |
| `PIP_INDEX_URL` | 官方 | 国内 PIP 加速 |
| `HTTP_PROXY` / `HTTPS_PROXY` / `http_proxy` / `https_proxy` | 空 | 构建期代理（构造完成后 `ENV` 清空，避免运行时污染） |
| `OPENCLAW_REPO_URL` | `https://github.com/higress-group/openclaw.git` | OpenClaw 源码地址（固定 commit `2f35b6fa…`） |
| `OPENCLAW_CMS_PLUGIN_URL` | ARMS OSS 上的插件包 | 可观测性插件（Worker/Manager） |

Makefile 级变量：`VERSION`、`REGISTRY`、`REPO`、`DOCKER_BUILD_ARGS`、`DOCKER_PLATFORM`、`MULTIARCH_PLATFORMS`、`BUILDX_BUILDER`、`HIGRESS_REGISTRY`。

### 3.4 命名构建上下文（BuildKit 必需）

`Makefile` 大量使用命名上下文，要求 Docker 23+ / BuildKit：

```makefile
SHARED_LIB_CTX    = --build-context shared=./shared/lib
COPAW_WORKER_CTX  = --build-context copaw-worker=./copaw
```

若报 `unknown flag: --build-context`，说明 BuildKit 未启用，需设 `DOCKER_BUILDKIT=1` 或升级 Docker。

### 3.5 本地构建标准命令（Docker）

```bash
# 1) 构建基底与 controller（必须先做）
make build-openclaw-base
make build-agentteams-controller

# 2) 用「本地基底」构建 manager / worker
#    必须成对指定 OPENCLAW_BASE_IMAGE + OPENCLAW_BASE_VERSION，否则会去拉远端 :latest
make build-manager build-worker \
    OPENCLAW_BASE_IMAGE=agentteams/openclaw-base \
    OPENCLAW_BASE_VERSION=latest

# 3) 其余运行时
make build-manager-qwenpaw build-copaw-worker build-qwenpaw-worker \
     build-hermes-worker build-openhuman-worker build-deepseek-harness-worker

# 4) 本地 embedded 镜像（本地 Docker 部署必需）
make build-embedded
```

带版本号构建：

```bash
make build VERSION=v1.2.3
```

国内网络（无代理）：

```bash
make build-openclaw-base DOCKER_BUILD_ARGS="--build-arg APT_MIRROR=mirrors.aliyun.com --build-arg NPM_REGISTRY=https://registry.npmmirror.com/"
make build-copaw-worker  DOCKER_BUILD_ARGS="--build-arg APT_MIRROR=mirrors.aliyun.com --build-arg PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/"
```

带代理（Docker Desktop：`host.docker.internal`；Podman on macOS：`host.containers.internal`）：

```bash
PROXY_ARGS="--build-arg HTTP_PROXY=http://host.docker.internal:1087 \
            --build-arg HTTPS_PROXY=http://host.docker.internal:1087 \
            --build-arg http_proxy=http://host.docker.internal:1087 \
            --build-arg https_proxy=http://host.docker.internal:1087"
make build-manager build-worker DOCKER_BUILD_ARGS="${PROXY_ARGS}"
```

指定平台：

```bash
make build-manager DOCKER_PLATFORM=linux/amd64
```

### 3.6 构建期易踩的坑

| 现象 | 根因 | 处置 |
|---|---|---|
| manager/worker 拉到了远端旧基底 | 本地构建基底后未成对覆盖 `OPENCLAW_BASE_IMAGE` + `OPENCLAW_BASE_VERSION` | 严格成对传参 |
| `unknown flag: --build-context` | BuildKit 关闭 | `DOCKER_BUILDKIT=1` |
| `make` 报 `missing separator` | `Makefile` 被转成 CRLF（Windows） | `git config --global core.autocrlf input` 后重检 |
| openclaw-base 构建超时 | clone/npm 无镜像源 | 传 `NPM_REGISTRY` 或代理 |
| controller 构建失败且 `agentteams-controller/agent` 残留 | Makefile 临时拷贝 `manager/agent` 目录后未清理 | 手动删除该临时目录后重试 |
| 构建容器内访问代理失败 | 用了 `127.0.0.1` | 改用 `host.docker.internal` |

## 四、镜像打标签与推送仓库

### 4.1 命名与打标规范

**镜像命名**：`<REGISTRY>/<REPO>/<image>:<TAG>`

- 默认 `REGISTRY=higress-registry.cn-hangzhou.cr.aliyuncs.com`、`REPO=agentteams`。
- CI 命名规则（`.github/workflows/build-image.yml`）：`openclaw-base` 与 `agentteams-controller` **保持原名**，其余目标加 `agentteams-` 前缀，例如 `target=worker` → `agentteams-worker`；`target=copaw-worker` → `agentteams-copaw-worker`。

**标签规范**：

| 标签 | 语义 | 规则 |
|---|---|---|
| `vX.Y.Z` | 发布版本 | 由 tag 触发，`VERSION` 取 `GITHUB_REF_NAME` |
| `vX.Y.Z-rc.N` / `-beta` / `-alpha` / `-pre` / `-preview` / `-dev` / `-snapshot` | 预发布 | 由 `Makefile` 的 `IS_PRERELEASE` 识别，**不推送 `:latest`** |
| `latest` | 最新稳定 | 仅稳定版本推送；`VERSION=latest` 时不再重复打 `latest` |
| `20260423-8359cbc` 形式 | 基底镜像日期+commit | `openclaw-base` 专用 |

本地打标（`make tag` 会先 `make build`）：

```bash
make tag VERSION=v1.2.3
# 等价于把 agentteams/manager:v1.2.3 → <REGISTRY>/agentteams/agentteams-manager:v1.2.3
# 并按规则附加 :latest（稳定版）
```

### 4.2 多架构推送（推荐方式）

```bash
# 首次会创建并 bootstrap buildx builder（agentteams-multiarch）
make push VERSION=v1.2.3

# 自定义平台
make push VERSION=v1.2.3 MULTIARCH_PLATFORMS=linux/amd64,linux/arm64

# 仅构建推送单个镜像
make push-worker VERSION=v1.2.3
make push-manager VERSION=v1.2.3
```

Makefile 会自动识别 Docker / Podman：
- Docker：`docker buildx build --platform ... --push`
- Podman：`podman build --platform <p> --manifest ...` 逐平台构建 + `podman manifest push --all`

**切勿**用 `make push-native` 做发布——单架构推送会**覆盖已有的多架构清单**，仅限本地开发调试。

### 4.3 推送至第三方仓库（Harbor / ACR / ECR）

仓库默认使用阿里云 ACR 风格地址；迁移到其他仓库时**先 tag 再 push**，并同步改 Helm values。通用步骤：

```bash
# 1) 登录
docker login harbor.example.com            # Harbor（需先建 project + robot 账号）
docker login <name>.azurecr.io             # ACR
aws ecr get-login-password --region <region> \
  | docker login --username AWS --password-stdin <acct>.dkr.ecr.<region>.amazonaws.com   # ECR

# 2) 重新 tag（保留版本与 latest 两个语义）
NEW=harbor.example.com/agentteams
for img in agentteams-controller agentteams-manager agentteams-worker \
           agentteams-copaw-worker agentteams-qwenpaw-worker agentteams-hermes-worker; do
  docker tag higress-registry.cn-hangzhou.cr.aliyuncs.com/agentteams/$img:v1.2.3 $NEW/$img:v1.2.3
  docker push $NEW/$img:v1.2.3
done

# 3) 多架构迁移可用 hack/mirror-images.sh（基于 skopeo，支持容器模式）
USE_CONTAINER=1 ./hack/mirror-images.sh
```

ECR 需先创建仓库：`aws ecr create-repository --repository-name agentteams/agentteams-worker`。

### 4.4 私有仓库拉取凭据

K8s `values.yaml` 支持 `imagePullSecrets`：

```yaml
imagePullSecrets:
  - name: agentteams-registry
```

```bash
kubectl create secret docker-registry agentteams-registry \
  -n agentteams-system \
  --docker-server=harbor.example.com \
  --docker-username=<user> \
  --docker-password=<pass>
```

### 4.5 CI 自动构建

| 工作流 | 触发 | 行为 |
|---|---|---|
| `build.yml` | tag `v*.*.*` / 手动 | 解析 version 与 targets（含依赖闭包）→ 分发调用 `build-image.yml` |
| `build-image.yml` | `workflow_call` | 构建单镜像多架构；**若已存在双架构清单则复用跳过** |
| `build-base.yml` | `openclaw-base/**` 变更 / 手动 | 构建推送 `openclaw-base:latest` |
| `build-rc.yml` | 手动 | RC 版本 |
| `build-deepseek-harness.yml` | DSH tag / 路径变更 / 手动 | 独立发布 DSH runtime |
| `release.yml` | tag 后由 `build.yml` 调用 | 校验版本与镜像存在 → 打 tag → 生成 Release → smoke test |
| `deploy-helm-to-oss.yml` | tag `v*.*.*` / 手动 | 打包 chart 并上传阿里云 OSS |

## 五、Kubernetes 资源清单与配置要点

### 5.1 Chart 概览

- 位置：`helm/agentteams/`，`Chart.yaml`：`version/appVersion 1.1.1`，依赖子 chart `higress 2.2.1`（`condition: gateway.higress.enabled`）。
- CRD 源真相：`agentteams-controller/config/crd/*.yaml` → `make sync-crds` → `helm/agentteams/crds/`。CI `check-crd-sync.yml` 强制一致。

### 5.2 资源总表

| 资源 | 模板 | 作用与要点 |
|---|---|---|
| `CustomResourceDefinition` ×4 | `crds/{workers,teams,humans,managers}.agentteams.io.yaml` | 定义 Worker/Team/Human/Manager 四类 CR；**Helm 不会自动删除 CRD** |
| `Deployment` | `templates/controller/deployment.yaml` | Controller 主进程（:8090），可挂 credential-provider sidecar |
| `ServiceAccount` / `Role` / `ClusterRole` + Binding | `templates/controller/{serviceaccount,rbac}.yaml` | Controller 调谐 CR、创建 Pod/SA、TokenReview 的权限 |
| `Service` | `templates/controller/service.yaml` | ClusterIP:8090，另有 metrics:8080（可选） |
| `ServiceMonitor` | `templates/controller/servicemonitor.yaml` | 可选，Prometheus Operator 场景 |
| `Job`（`pre-delete` hook） | `templates/controller/uninstall-hook.yaml` | `helm uninstall` 前按 Manager→Worker→Team→Human 删除 CR，等 finalizer 清理 |
| `StatefulSet` + `Service` | `templates/matrix/tuwunel-*.yaml` | Matrix Homeserver，:6167，PVC 持久化 |
| `StatefulSet` + `Service` + `Secret` | `templates/storage/minio-*.yaml` | 对象存储，API 9000 / Console 9001，PVC 持久化 |
| `Deployment` + `Service` + `ConfigMap` | `templates/element-web/*.yaml` | 可选 IM 前端（:8080），ConfigMap 注入 `config.json` |
| `Secret` | `templates/secrets/runtime-env.yaml` | 共享运行时 Secret：注册令牌、admin、LLM Key、AppService token；用 `lookup` 保留已有值 |
| `Job`（`pre-install`/`pre-upgrade` hook） | `templates/preflight/llm-job.yaml` + `llm-secret.yaml` | 调用 `agt llm-preflight` 探测 LLM 连通性；`strict=true` 时失败即阻断安装 |
| Higress 子 chart | 由依赖渲染 | 网关（Gateway/Controller/Console），ClusterIP，供 `kubectl port-forward` 暴露 |
| 渲染期校验 | `templates/00-validate.yaml` | 校验 provider/mode 组合与必填项，非法组合直接 `fail` |
| 基础设施抽象 helper | `templates/_helpers.infra.tpl` | 推导 matrix/gateway/storage 的 URL、endpoint、bucket、Manager spec |

### 5.3 关键配置要点

**（1）非法组合在渲染期就被拒绝**（`00-validate.yaml`）：

- `matrix.provider` 仅 `tuwunel`，`matrix.mode` 仅 `managed`；
- `gateway.provider=higress` 必须 `mode=managed`；`ai-gateway` 必须 `mode=existing`，且 `gatewayId`、`region` 必填；
- `storage.provider=minio` 必须 `managed`；`oss` 必须 `existing`，且 `oss.region` 必填；
- `gateway.publicURL` 为必填；
- 任一云 provider（ai-gateway / oss）必须启用并配置 `credentialProvider`。

**（2）Secret 生成与保留**：`agentteams-runtime-env` 中 `registrationToken`、`adminPassword`、AppService `as/hs_token` 为空时自动随机生成；已有值通过 Helm `lookup` 保留，避免升级时轮换导致客户端失联。`credentials.llmApiKey` 为 `required`，缺失则渲染失败。

**（3）Controller Deployment 关键环境变量**：`AGENTTEAMS_KUBE_MODE=incluster`、`AGENTTEAMS_RUNTIME=k8s`、`AGENTTEAMS_WORKER_BACKEND=k8s`、各 runtime 的 Worker 镜像地址、`AGENTTEAMS_RESOURCE_PREFIX`（多实例隔离）、`AGENTTEAMS_CONTROLLER_NAME`。

**（4）Pod 模板覆盖（ConfigMap）**：Controller 会读取**与 Controller 同名的 ConfigMap**（键 `pod-template.yaml`）作为 Manager/Worker Pod 的 `PodTemplateSpec` 叠加层——这是给所有 Agent Pod 注入 `nodeSelector`/`tolerations`/`sysctls`/`imagePullSecrets` 的官方入口。ConfigMap 不存在则无叠加。

**（5）Registry 覆盖陷阱**：`global.imageRegistry` 虽会传给子 chart，但 Controller/Manager/Worker 的 values 使用的是**完整的 `repository` 路径**。换仓库时必须逐个覆盖 `controller.image.repository`、`manager.image.repository`、`worker.defaultImage.<runtime>.repository`，不要只改 `global.imageRegistry`。

**（6）Ingress 不由 Chart 模板化**：官方做法是 `kubectl port-forward`；共享访问需自行编写 Ingress，指向 `higress-gateway:80`，并把同一 origin 写回 `gateway.publicURL`。

**（7）Manager runtime = 镜像要成对改**：

```yaml
manager:
  runtime: qwenpaw
  image:
    repository: higress-registry.cn-hangzhou.cr.aliyuncs.com/agentteams/agentteams-manager-qwenpaw
```

只改 `runtime` 不改 `image` 会导致 Manager Pod 起不来或行为错配。

### 5.4 推荐 values 片段

```yaml
credentials:
  llmApiKey: "<your-api-key>"
  llmProvider: openai-compat
  defaultModel: gpt-5.4
  llmBaseUrl: ""
  adminUser: admin
  adminPassword: "<strong-password>"

gateway:
  provider: higress
  mode: managed
  publicURL: http://localhost:18080
  higress: { enabled: true }

matrix:   { provider: tuwunel, mode: managed, tuwunel: { persistence: { enabled: true, size: 10Gi } } }
storage:  { provider: minio,  mode: managed, bucket: agentteams-storage,
            minio: { persistence: { enabled: true, size: 10Gi },
                     auth: { rootUser: minioadmin, rootPassword: "<strong-password>" } } }

preflight: { llm: { enabled: true, strict: true } }
manager:   { enabled: true, runtime: openclaw }
worker:    { defaultRuntime: openclaw }
```

## 六、端到端上线流程（镜像 → Pod → 服务暴露）

### 6.1 路径 A：Docker（本地 embedded）上线

**Step 1 构建镜像**

```bash
make build-embedded build-manager build-manager-qwenpaw build-worker \
     build-copaw-worker build-qwenpaw-worker build-hermes-worker \
     OPENCLAW_BASE_IMAGE=agentteams/openclaw-base OPENCLAW_BASE_VERSION=latest
```

**Step 2 安装（拉起容器）**

```bash
AGENTTEAMS_LLM_API_KEY=sk-xxx AGENTTEAMS_NON_INTERACTIVE=1 \
  bash install/agentteams-install.sh manager
# 或完整 embedded：
AGENTTEAMS_LLM_API_KEY=sk-xxx make install-embedded
# Windows： .\install\agentteams-install.ps1 manager
```

安装器创建：`agentteams-net` 网络、`agentteams-data` 数据卷、`agentteams-controller` 容器（内含 Higress/Tuwunel/MinIO/Element Web/Controller）、`agentteams-manager` 容器（由 controller 拉起）、可选 `agentteams-dashboard`。

**Step 3 拉起镜像地址覆盖（本地构建时）**：通过 `AGENTTEAMS_INSTALL_EMBEDDED_IMAGE` / `AGENTTEAMS_INSTALL_MANAGER_IMAGE` / `AGENTTEAMS_INSTALL_WORKER_IMAGE` 等变量指向本地 tag。

**Step 4 等待就绪并验证**

```bash
make wait-ready-embedded          # 轮询 Matrix(6167)/MinIO(9000)/Console(8001) 并等待 60s 初始化
make verify                       # install/agentteams-verify.sh 只读 7 项连通性校验
docker exec agentteams-controller agt get managers
docker exec agentteams-controller agt get workers
```

**Step 5 访问**

| 入口 | 地址 |
|---|---|
| Element Web | `http://127.0.0.1:18088/#/login` |
| Higress Console | `http://127.0.0.1:18001` |
| Dashboard | `http://127.0.0.1:13000` |

**Step 6 首个 Worker**：在 Element Web 登录 admin，向 Manager 发消息「创建名为 alice 的 Worker」，Controller 通过 Docker socket 创建 `agentteams-worker-alice` 容器。

### 6.2 路径 B：Kubernetes 上线

**Step 1 构建并推送镜像**

```bash
make push VERSION=v1.2.3
# 或构建后用 kind load（本地验证）
```

**Step 2 前置检查**

```bash
kubectl version && kubectl cluster-info && kubectl get storageclass && helm version
```

**Step 3 编写 values 文件**（见 5.4），`chmod 600 agentteams-values.yaml`

**Step 4 安装/更新**

```bash
helm dependency build helm/agentteams
helm upgrade --install agentteams ./helm/agentteams \
  --namespace agentteams-system --create-namespace \
  --values agentteams-values.yaml \
  --set global.imageTag=v1.2.3 \
  --render-subchart-notes --wait --timeout 15m
```

注意：Chart `appVersion=1.1.1` 会推导出 `v1.1.1` tag。源码树验证时可临时 `--set global.imageTag=latest`，生产必须固定已发布版本。

**Step 5 渲染核对（先看再装）**

```bash
helm template agentteams ./helm/agentteams -n agentteams-system \
  -f agentteams-values.yaml | grep 'image:' | sort -u
```

**Step 6 资源就绪校验**

```bash
helm status agentteams -n agentteams-system
kubectl get pods,pvc -n agentteams-system
kubectl wait --for=condition=Ready pod --all -n agentteams-system --timeout=15m
kubectl get managers.agentteams.io -n agentteams-system     # PHASE 应为 Running
kubectl get pods -n agentteams-system -l agentteams.io/role=manager
```

**Step 7 服务暴露**

```bash
# 临时
kubectl port-forward -n agentteams-system svc/higress-gateway 18080:80
# 读取自动生成的 admin 密码
kubectl get secret agentteams-runtime-env -n agentteams-system \
  -o go-template='{{index .data "AGENTTEAMS_ADMIN_PASSWORD" | base64decode}}{{"\n"}}'
```

生产用 Ingress（示例，指向 `higress-gateway:80`，并在 values 中把 `gateway.publicURL` 设为同一 HTTPS origin）。

**Step 8 创建 Worker 并闭环验证**

```bash
kubectl apply -f worker-alice.yaml
kubectl get workers.agentteams.io -n agentteams-system
kubectl get pods -n agentteams-system -l agentteams.io/role=standalone
```

在 Element Web 中对 Worker 完整 Matrix ID 发 `@mention` 任务，确认回复。Worker 群房间默认 `requireMention`，事件必须包含 `m.mentions.user_ids`。

### 6.3 Pod 创建链路（K8s 声明式资源流）

```
用户/Manager 提交 Worker|Team|Human|Manager CR（agt apply / REST API / kubectl apply）
        │
        ▼
agentteams-controller（server/resource_handler.go 写入 CR）
        │
        ▼
Reconciler（internal/controller/*）
   ├─ service/Provisioner  → Matrix 用户/房间、网关消费者、MinIO 用户、ServiceAccount
   ├─ service/Deployer     → 生成 openclaw.json / AGENTS.md / runtime.yaml 落对象存储
   ├─ backend/kubernetes   → 创建 Pod（+ 可选 ConfigMap pod-template 叠加）
   └─ gateway/ + credprovider → 绑定模型路由与 STS 凭据
        │
        ▼
Worker/Manager 运行时容器（agentteams-env.sh 引导 → 从 MinIO 拉配置 → 以 Matrix 为唯一通道）
```

`backend/kubernetes.go` 的 Pod 形态：容器名固定 `worker`，`ImagePullPolicy=IfNotPresent`，注入 `Env`/`WorkingDir`/资源限制/ServiceAccount/投影 token 卷，并打上系统标签 `agentteams.io/{controller,worker|manager,role,runtime}` + `app`（用户同名标签会被静默覆盖）。

## 七、滚动更新、回滚与探针机制

### 7.1 探针配置现状（重要）

| 工作负载 | 就绪探针 | 存活探针 |
|---|---|---|
| **Controller Deployment** | `httpGet /healthz`（:8090，initialDelay 5s，period 10s） | `httpGet /healthz`（initialDelay 30s，period 20s，failureThreshold 3） |
| credential-provider sidecar | `httpGet /healthz`（initialDelay 2s） | `httpGet /healthz`（initialDelay 15s） |
| Tuwunel StatefulSet | `tcpSocket 6167`（5s/10s） | `tcpSocket 6167`（10s/20s） |
| MinIO StatefulSet | `httpGet /minio/health/ready`（:api，5s/10s） | `httpGet /minio/health/live`（:api，10s/20s） |
| Element Web Deployment | `httpGet /`（:http，5s/10s） | `httpGet /`（:http，10s/20s） |
| **Manager / Worker Agent Pod** | **无 K8s 探针** | **无 K8s 探针** |

Manager / Worker Pod 的就绪状态由 Controller 侧维护：`POST /api/v1/workers/{name}/ready`、`/heartbeat`、`GET /api/v1/workers/{name}/status`，以及 `agt worker ensure-ready|status` 命令；CR 的 `PHASE`（如 `Running`）是判断依据。运维诊断应查 **CR 状态 + Controller 日志**，而非 `kubectl describe pod` 的探针字段。

### 7.2 滚动更新

- **Controller / Element Web（Deployment）**：默认 `RollingUpdate`，`helm upgrade` 触发；`--wait` 会阻塞到新 Pod 就绪。
- **Tuwunel / MinIO（StatefulSet）**：默认 `RollingUpdate`，单副本场景等价于"重建"，**升级前必须备份 PVC 内数据**。
- **Manager / Worker Pod**：由 Controller 直接管理，不是 Deployment，因此**没有滚动更新语义**。改 `manager.runtime`、`manager.image` 或 Worker 镜像会导致 Pod **重建**，应在无任务运行时进行。
- **Higress 子 chart**：由依赖升级驱动。

### 7.3 版本回滚

```bash
# 1) 查看历史
helm history agentteams -n agentteams-system

# 2) 回滚到上一版本（镜像 tag 随 values 一起回滚）
helm rollback agentteams -n agentteams-system --wait --timeout 15m

# 3) 仅回滚镜像 tag（推荐，最小影响面）
helm upgrade agentteams ./helm/agentteams -n agentteams-system \
  -f agentteams-values.yaml --set global.imageTag=v1.2.2 --wait

# 4) 对 Deployment 做单点回滚（Controller / Element Web）
kubectl rollout undo deployment/agentteams-controller -n agentteams-system
kubectl rollout status deployment/agentteams-controller -n agentteams-system
```

回滚边界与注意：
- **CRD 不会被 Helm 回滚**，也不随 `helm uninstall` 删除；
- PVC 数据不回滚，需依赖备份；
- 回滚后仍需 `kubectl get managers/workers.agentteams.io` 确认 PHASE 恢复；
- 若回滚涉及 `manager.runtime`/镜像切换，Manager Pod 会重建。

## 八、注意事项、常见问题与验证方式

### 8.1 构建期

| 问题 | 排查/处置 |
|---|---|
| 拉基底镜像慢/失败 | 传 `HIGRESS_REGISTRY`，国内用 cn-hangzhou，北美用 us-west-1 |
| npm/pip/apt 超时 | 传 `NPM_REGISTRY`/`PIP_INDEX_URL`/`APT_MIRROR` 或代理 |
| 多架构构建失败 | 确认 `docker buildx inspect agentteams-multiarch` 正常；Windows 需 WSL2 后端支持 QEMU |
| worker 中 `lsof` 卡死（Kind） | 镜像已内置 stub，无需处理；自定义基底时需保留该处理 |
| `agentteams-controller/agent` 残留 | Makefile 临时目录未清理，手动删除 |

**验证**：`docker images | grep agentteams`、`docker run --rm <image> <entrypoint> --help`（或 `agt --help`）、`docker inspect <image> | grep Architecture`。

### 8.2 推送/拉取期

| 问题 | 排查/处置 |
|---|---|
| `ImagePullBackOff` | 节点能否访问仓库、tag 是否存在、CPU 架构是否匹配、是否配 `imagePullSecrets` |
| 别名镜像 tag 不存在（如 `agentteams-controller:v1.1.1`） | `helm template ... | grep image:` 核对，明确 `--set global.imageTag` |
| 误用 `push-native` 覆盖多架构清单 | 发布一律 `make push`；`docker buildx imagetools inspect <ref>` 核对双架构 |
| Preflight Job 报 `ImagePullBackOff` | preflight 复用 Controller 镜像，Controller tag 缺失会先在 hook 阶段暴露 |

**验证**：`docker manifest inspect <ref>` 或 `docker buildx imagetools inspect <ref>` 显示 `linux/amd64` + `linux/arm64`。

### 8.3 部署期

| 问题 | 排查/处置 |
|---|---|
| 卡在 LLM preflight | 校验 Key/provider/model/BaseURL 与集群出网；或临时 `preflight.llm.strict=false`；`helm install --debug` |
| Pod `Pending` | `kubectl describe pod`、`kubectl get events --sort-by=.lastTimestamp`、检查 StorageClass/PVC/taint/配额 |
| PVC `Pending` | 集群有无默认 StorageClass，或显式指定 `storageClassName` |
| Helm 渲染失败 | 检查 `00-validate.yaml` 约束的组合（provider/mode/credentialProvider） |
| Higress values 类型告警 | 只要 Release 到 `deployed` 且 Higress Pod Ready，该告警不阻断 |
| Manager CR 存在但 Pod 未就绪 | `kubectl describe manager default`、Controller 日志；常见因 runtime/镜像不匹配、资源不足、依赖未就绪 |
| Element Web 打开但登录/连不上 Matrix | `gateway.publicURL` 与浏览器 origin 是否一致；`curl -I https://<host>/_matrix/client/versions`；Ingress 需支持 WebSocket 与长连接 |

### 8.4 运行期

| 问题 | 排查/处置 |
|---|---|
| Worker 在群房间不回复 | 确认是**完整 Matrix ID 提及**且事件含 `m.mentions.user_ids`；查 `matrix-auto-reply skipping room message` |
| 消息是否进模型 | `kubectl logs -l agentteams.io/role=standalone --tail=200 \| grep -E 'resolveAgentRoute\|embedded run start\|model='` |
| 本地端口冲突 | 18080/18001/18088/13000（本地）与 18080（kind NodePort 映射） |
| Manager Agent 启动超时 | WSL2 内存不足（`.wslconfig: memory=8GB`）、资源限制过低 |
| 卸载残留 | `helm uninstall` 有 `pre-delete` hook 清理 CR，**切勿随意 `--no-hooks`**；CRD 与 PVC 需手工确认后删除 |

### 8.5 统一验收清单

**Docker 路径**
1. `docker ps --filter name=agentteams` → controller / manager Running
2. `make verify` → 7 项 PASS
3. `docker exec agentteams-controller agt get managers` → 有 Manager 且 Running
4. Element Web 登录并发一条消息，确认模型回复
5. 让 Manager 创建 Worker → `agt get workers` → 容器出现

**K8s 路径**
1. `helm status` = `deployed`
2. `kubectl get pods -n agentteams-system` 基础设施全 Ready；`kubectl get pvc` 全 Bound
3. `kubectl get managers.agentteams.io` PHASE = `Running`
4. Element Web 登录 → 发消息 → 收到模型回复（Pod Ready ≠ 推理可用）
5. 创建 Worker → CR 与 Pod Ready → @mention 发任务 → 房间内收到结果
6. `kubectl logs ... | grep 'embedded run start'` 确认消息进入模型路径
